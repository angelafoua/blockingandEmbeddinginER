# Parameter Insensitivity Investigation: algo_1_2_v2

## Overview

The `Algo1_2_v2/recursive_algo1_2_v2.py` pipeline exhibits **parameter insensitivity**: modifying the `do_merge` and `do_purge` parameters produces identical results when `do_purge=True`. This investigation identifies the root cause and provides concrete fixes.

## Critical Finding

**The pipeline is parameter-insensitive ONLY when `do_purge=True`.**

When `do_purge=False`, parameters work correctly and outputs vary as expected.

## Evidence

### Experiment 1: Parameter Variations with Purging

With `do_purge=True`:
```
Configuration: (merge=True, purge=True)
  Beta 1 → 2: Blocks go from 16,188 → 10,457, but after purge: 2,068 → 2,068
  Beta 2 → 3: Blocks go from 10,457 → 6,765, but after purge: 2,068 → 2,068
  Beta 3 → 4: Blocks go from 6,765 → 5,087, but after purge: 2,068 → 2,068
  
Final candidate pairs across all configs: 173,877 (IDENTICAL!)
```

With `do_purge=False`:
```
Configuration: (merge=True, purge=False)
  Beta 1 → 2: 16,188 → 16,643 blocks
  Beta 2 → 3: 16,643 → 16,671 blocks
  Beta 3 → 4: 16,671 → 16,674 blocks
  
Final candidate pairs: 236,719 (DIFFERENT!)
```

### Experiment 2: What Blocks Survive?

Blocks that survive the `purge_subset_blocks()` function:
- **2,068 simple single-token blocks**: `TOMMY`, `ALAN`, `VENTURA`, `AVENUE`, etc.
- Average size: 10-50 records per block

Blocks that get dropped:
- **14,120 complex multi-token blocks** (from Beta 1 alone)
- Examples: `('754', '93003', 'VENTURA')`, `('FONTANA', 'RUBEN', 'RODRIGTUE', '92336', 'TUSCANY')`
- Average size: 1-5 records per block
- **These are the refined blocks produced by `refine_blocks()`!**

### Experiment 3: Why Refined Blocks Are Dropped

Example: Complex block `('754', '93003', 'VENTURA')` containing 5 records:
```
{A918922, B932814, A965806, B919821, B910363}
```

The `purge_subset_blocks()` algorithm:
1. Finds ALL blocks containing these exact 5 records
2. Result: 2 blocks
   - `VENTURA` (17 records) — superset
   - `('754', '93003', 'VENTURA')` (5 records) — itself
3. Since `VENTURA` has more records, the refined block is a **strict subset**
4. **The refined block gets dropped**

This repeats for every beta iteration, preventing refinement accumulation.

## Root Cause: Design Incompatibility

### The Algorithm's Intended Purpose

The `purge_subset_blocks()` function (lines 117-165) was designed for **single-pass blocking**:
```
blocks = {
    'VENTURA': {record_set_1},
    'ALAN': {record_set_2},
    ...
}
↓ (remove subsets)
blocks = {
    'VENTURA': {record_set_1},
    'ALAN': {record_set_2},
    ...  (only maximal blocks remain)
}
```

The idea: If block A contains all records of block B, then all intra-block pairs from B are also generated by A, so B is redundant.

### The Algorithm's Actual Context

But the function is called in an **iterative refinement context**:
```
Initial blocks (single tokens):
  'VENTURA': {rec1, rec2, rec3, ..., rec17}

After Beta 1 refinement:
  'VENTURA': {rec1, rec2, ..., rec17}  (original)
  ('754', 'VENTURA'): {rec1, rec3, rec5} (refined, subset of above!)
  ('93003', 'VENTURA'): {rec2, rec4, rec6}
  ... (many more refined blocks)

After merge: {original blocks + refined blocks} = 16,188 blocks

After purge: {2,068 blocks} (all refined blocks removed because they're subsets!)
```

### The Fundamental Incompatibility

In refinement contexts, refined blocks **must be subsets** of their parent blocks (because you're adding constraints). But the purging function removes exactly these subsets, negating all refinement work.

## Impact Analysis

### When `do_purge=True` (Parameter Insensitive)
- Beta threshold parameter has **zero effect** on output
- All refinement iterations produce the same result
- Candidate pair counts are deterministic regardless of beta
- The algorithm behaves like a single-pass blocker, not an iterative refiner

### When `do_purge=False` (Parameter Sensitive)
- Beta threshold parameter **correctly affects** output
- Refinement iterations accumulate as expected
- Block count grows from 16K to 142K across beta iterations
- Algorithm works as intended (though without subset elimination)

## Recommended Fixes

### Fix 1: Don't Purge During Iteration (Recommended)

Change the default and skip purging within the loop:
```python
def recursive_blocking(beta, blocks, stop_k, do_merge=True, do_purge=True):
    # ... refinement loop ...
    
    if do_purge:
        print(f"Purging subset blocks...")
        # Only purge AFTER all iterations complete
    else:
        # Current behavior
        print(f"Skipping purge_subset_blocks (do_purge=False)")
    
    # Only call purge OUTSIDE the recursion:
    # if do_purge:
    #     blocks = purge_subset_blocks(blocks)
    # return blocks
```

Modify `run_pipeline()` to purge only at the end:
```python
def run_pipeline(initial_blocks, stop_k, all_refIDs, do_merge, do_purge,
                 top_k=3, tau=1.0):
    # ... run recursive_blocking ...
    final_blocks = recursive_blocking(1, blocks_in, stop_k,
                                      do_merge=do_merge, do_purge=False)
    
    # Apply purging ONLY once at the end
    if do_purge:
        final_blocks = purge_subset_blocks(final_blocks)
    
    # ... continue with filtering and clustering ...
```

### Fix 2: Purge Only New Blocks

Purge the newly created blocks before merging with old ones:
```python
newBlocks = refine_blocks(blocks, beta)

if do_purge:
    print(f"Purging new blocks only...")
    newBlocks = purge_subset_blocks(newBlocks)

merged_blocks = merge_blocks(blocks, newBlocks)
```

This preserves accumulated refinements while removing internal redundancies.

### Fix 3: Change Stopping Condition

Stop when no new blocks are created (natural convergence):
```python
newBlocks = refine_blocks(blocks, beta)

if not newBlocks:
    print("Stopping: no new blocks created")
    return blocks
```

This eliminates dependency on the `stop_k` heuristic.

## Conclusion

The parameter insensitivity is caused by the `purge_subset_blocks()` function being applied during each iteration of the refinement loop. Since refined blocks are inherently subsets of their parent blocks, they get removed in each iteration, preventing refinement accumulation.

The fix is to **change when purging happens**: either move it to after all iterations complete, or apply it only to newly created blocks before merging with old ones.
